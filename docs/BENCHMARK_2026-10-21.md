# Razor 0.1.0-rc.1：100 MiB CDN 场景验证与压力报告

日期：2026-10-21 UTC。关联 [#15](https://github.com/Monsterwi/bakemono/issues/15)，总计划 [#1](https://github.com/Monsterwi/bakemono/issues/1) 保持打开。

## 结果与统计口径

专用测试机上 HDD、SSD 的主矩阵均完成，每种介质 47 批，合计 **94 批、342,271 请求、批次非预期错误 0**。其中 **60 个 503** 来自两次主动设置 `max_requests=2 / queue=0` 的过载测试，单列为预期拒绝。HDD 为 171,425 请求（170,389×200、1,006×206、30×503），SSD 为 170,846 请求（169,810×200、1,006×206、30×503）。

每种介质的完整功能矩阵均为 **19 PASS / 1 LIMITATION**。负向功能探测不并入上述并发批次分母：例如主动截断、SIGKILL、旧 follower 被 PURGE 失效、源站不健康与超容量请求，其状态/连接错误按各自硬断言验收。不得直接将 `requests.jsonl` 中所有 `error` 字段当作随机故障率，也不得把已知限制计为通过。

Go 客户端交叉测量与块层冷读单独统计，不与主矩阵混成一种客户端的性能结果。预检运行也不计入正式数字。

## 主矩阵：逐响应 SHA256 校验

Python 客户端仅保留 64 KiB 流式缓冲，对每个正常 200/206 正文校验长度与 SHA256，不为每个客户端分配整个 100 MiB 正文。吞吐、CPU/GiB 为三次中位数；p99 为三批中最高分位值，未混合成一个分位数。时间窗口结束后完成在途请求，因此大文件批次可超过目标 10 秒。

最终使用正文读取检查版 hey，共 **24 批、1,680,294 请求**（HDD 836,214、SSD 844,080），所有成功记录为 200，实际正文读取无错误，每批累计实际字节数与预期一致；前后 SHA256 一致且源站计数不增加。hey 不逐响应计算 hash，这与主矩阵逐响应 hash 的口径分开。以下各档均为 10 秒、3 次重复，吞吐/QPS/CPU 取中位数，p99 取三批最大值。

最小实测块读取比例为 **99.91%**。冷读表是 HTTP 对象交付的端到端速度，包含校验、复制和发送，不是裸盘顺序读。每次只有一个请求，故报告总耗时，不从 3 个请求推导生产 p99。hey 单样本的无意义 p0=0 已由驱动过滤。

## 测量边界与已知问题

- 本轮是专用机器上的合成 CDN 工作负载，不是生产公网压测或长期稳定性验收。服务、源站与施压客户端共享主机，loopback 不经过物理网卡；不能将吞吐直接写成公网 CDN 带宽或单机生产上限。
- 主矩阵的 SHA256/解释器调度会影响容量。hey 使用不同校验策略，数据必须单列；两类客户端吞吐差异不是服务代码优化收益。
- 热集远小于系统内存，普通文件 buffered I/O 会命中 OS page cache。热吞吐不是 HDD/SSD 裸盘速度；没有更改后端为 O_DIRECT 或逐对象 fsync。
- 初次工具在重启前逐出文件缓存，但恢复扫描重新读取了完整正文，实测 read_bytes=0；主矩阵的 `large-file-cache-cold-*` 仅算重启后的缓存命中，不作为盘冷读证据。追加工具改为恢复后、无在途请求时，仅对本项目缓存文件 fsync+fadvise，再以实际块 I/O 计数验证。未全局 drop_caches，也未清控制器或设备缓存。
- 工具预检还发现块 I/O 计数略小于对象长度，旧的 100% 门槛未满足，原失败记录保留。正式测量采用显式 99% 门槛并逐次公布实际字节数；预检不计入正式负载及错误分母。
- 所有源站摘除时 fresh 完整对象仍 HIT，但已缓存 Range 返回 502；每介质一项 LIMITATION，见 [#16](https://github.com/Monsterwi/bakemono/issues/16)。不具备该条件下的 Range 离线可用性，也没有 stale-if-error。
- 现有 TLS/HTTP/2、存储失败与并发隔离由 Go 集成/回归验证；本轮容量表没有覆盖 TLS/H2、HTTP/3、跨机客户端、公网丢包/RTT、真实磁盘 ENOSPC、掉电或数小时 soak。新 ATS 10.2 尚未安装/适配，本报告不作 ATS 性能排名。
