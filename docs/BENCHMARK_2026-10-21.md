# Razor 0.1.0-rc.1：100 MiB CDN 场景验证与压力报告

日期：2026-10-21 UTC。关联 [#15](https://github.com/Monsterwi/bakemono/issues/15)，总计划 [#1](https://github.com/Monsterwi/bakemono/issues/1) 保持打开。

## 结果与统计口径

专用测试机上 HDD、SSD 的主矩阵均完成，每种介质 47 批，合计 **94 批、342,271 请求、批次非预期错误 0**。其中 **60 个 503** 来自两次主动设置 `max_requests=2 / queue=0` 的过载测试，单列为预期拒绝。HDD 为 171,425 请求（170,389×200、1,006×206、30×503），SSD 为 170,846 请求（169,810×200、1,006×206、30×503）。

每种介质的完整功能矩阵均为 **19 PASS / 1 LIMITATION**。负向功能探测不并入上述并发批次分母：例如主动截断、SIGKILL、旧 follower 被 PURGE 失效、源站不健康与超容量请求，其状态/连接错误按各自硬断言验收。不得直接将 `requests.jsonl` 中所有 `error` 字段当作随机故障率，也不得把已知限制计为通过。

Go 客户端交叉测量与块层冷读单独统计，不与主矩阵混成一种客户端的性能结果。预检运行也不计入正式数字。

## 主矩阵：逐响应 SHA256 校验

Python 客户端仅保留 64 KiB 流式缓冲，对每个正常 200/206 正文校验长度与 SHA256，不为每个客户端分配整个 100 MiB 正文。吞吐、CPU/GiB 为三次中位数；p99 为三批中最高分位值，未混合成一个分位数。时间窗口结束后完成在途请求，因此大文件批次可超过目标 10 秒。

下表成对数字均为 HDD / SSD。CPU 是服务进程 user+system CPU 秒/GiB，不含源站和客户端的 CPU。

| 256 KiB / 8 | 448.25 / 442.84 | 1.618 / 1.667 | 1.40 / 1.46 | 6.75 / 6.86 | 53943 / 53365 |
| 256 KiB / 32 | 435.33 / 430.68 | 1.683 / 1.694 | 2.62 / 2.75 | 11.55 / 11.79 | 52144 / 51467 |

主矩阵资源采样峰：HDD RSS **128.30 MiB**，SSD RSS **125.68 MiB**；FD 均为 **115**，goroutine 均为 **210**。100 ms 资源采样和 500 ms SIGUSR1 仅能给出采样峰，不能证明瞬时上界或长期无泄漏。

混合热集 32 并发吞吐中位数为 HDD **1307.70 MiB/s**、SSD **1318.55 MiB/s**；16 MiB 热 Range、32 并发分别为 **738.29 / 759.08 MiB/s**，CPU **5.581 / 5.308 CPU秒/GiB**。Range 的单位流量 CPU 高于完整对象，值得剖析重复块读取、校验和分配；本轮没有用 pprof 确定热点占比。

冷 100 MiB / 32 并发的首字节 p99 为 **580.16 / 591.50 ms**，完成 p99 **2937.68 / 2918.22 ms**。慢源站组首字节 p99 约 **1913.97 / 1904.18 ms**。这些结果体现完整提交后交付的延迟成本，不是流式 RWW。

## Go 客户端交叉测量与文件页缓存冷读

正式 hey 热缓存共 **24 批、1,667,589 请求**（HDD 825,938、SSD 841,651），所有记录均为 200，未观察到传输错误；每批前后 SHA256 一致且源站计数不增加。hey 不逐响应计算 hash，统计的正文长度来自 Content-Length；这一口径与主矩阵的逐响应长度/hash 校验分开。以下各档均为 10 秒、3 次重复，吞吐/QPS/CPU 取中位数，p99 取三批最大值。

| 对象 / 并发 | HDD / SSD MiB/s | HDD / SSD QPS | HDD / SSD 完成 p99 ms | HDD / SSD CPU秒/GiB | 三批请求数 HDD / SSD |
| --- | ---: | ---: | ---: | ---: | ---: |
| 256 KiB / 32 | 3571.40 / 3671.35 | 14285.59 / 14685.40 | 5.55 / 5.44 | 1.557 / 1.522 | 429595 / 443088 |
| 256 KiB / 100 | 3282.54 / 3310.15 | 13130.15 / 13240.59 | 13.35 / 13.11 | 1.606 / 1.581 | 394038 / 396190 |
| 100 MiB / 8 | 3833.79 / 4066.27 | 38.34 / 40.66 | 239.23 / 218.97 | 2.109 / 1.981 | 1172 / 1231 |
| 100 MiB / 32 | 3606.11 / 3677.74 | 36.06 / 36.78 | 1130.14 / 1146.78 | 2.645 / 2.571 | 1133 / 1142 |

hey 服务进程的采样峰 RSS 为 **121.38 / 120.99 MiB**，FD 均为 **134**。同一二进制在不同客户端下出现很大吞吐差异，说明 Python 校验客户端会限制容量；不能拿两组数值相除宣传成代码优化。热缓存达到 GiB/s 的数据来自 RAM/OS page cache 和 loopback，不是机械盘或 SATA SSD 的介质吞吐，也不是物理网卡或公网带宽。

追加 **6 次**文件页缓存冷读，HDD/SSD 各 3 次；每次正常重启后等待恢复完成，fsync 并对本项目静止缓存文件执行 POSIX_FADV_DONTNEED，然后由 hey 单连接完整读取 100 MiB。实际块 I/O 要求至少为对象大小的 99%，SHA256 在测量后复核，源站新增请求为 0。fadvise 只是建议，不能保证每页都被清除；最小实测比例为 **99.88%**，也没有控制硬件缓存。

| 介质 | 三次交付 MiB/s | 中位 MiB/s | 单次总耗时 ms | 实际块读取字节 |
| --- | --- | ---: | --- | --- |
| SAS HDD | 161.62 / 167.81 / 168.53 | 167.81 | 618.73 / 595.92 / 593.36 | 104833024 / 104845312 / 104734720 |
| SATA SSD | 244.19 / 218.67 / 257.79 | 244.19 | 409.51 / 457.31 / 387.91 | 104792064 / 104833024 / 104865792 |

冷读表测量的是 HTTP 对象从缓存交付的端到端速度，包含记录校验、内存复制与网络发送，不是裸盘顺序读。每次只有一个请求，因此报告总耗时，不从 3 个请求推导生产 p99。hey v0.1.4 在单样本时会输出无意义的 p0=0；未将它用于表格，最终工具过滤了该项。

主矩阵结束后，两介质最后的资源快照均为 InFlight/Queued/CacheWriters/SharedFillTasks/SharedFillWaiters=0，goroutine=7。仅代表本轮结束时已排空，不代表长时间无泄漏。

## 测量边界与已知问题

- 本轮是专用机器上的合成 CDN 工作负载，不是生产公网压测或长期稳定性验收。服务、源站与施压客户端共享主机，loopback 不经过物理网卡；不能将吞吐直接写成公网 CDN 带宽或单机生产上限。
- 主矩阵的 SHA256/解释器调度会影响容量。hey 使用不同校验策略，数据必须单列；两类客户端吞吐差异不是服务代码优化收益。
- 热集远小于系统内存，普通文件 buffered I/O 会命中 OS page cache。热吞吐不是 HDD/SSD 裸盘速度；没有更改后端为 O_DIRECT 或逐对象 fsync。
- 初次工具在重启前逐出文件缓存，但恢复扫描重新读取了完整正文，实测 read_bytes=0；主矩阵的 `large-file-cache-cold-*` 仅算重启后的缓存命中，不作为盘冷读证据。追加工具改为恢复后、无在途请求时，仅对本项目缓存文件 fsync+fadvise，再以实际块 I/O 计数验证。未全局 drop_caches，也未清控制器或设备缓存。
- 工具预检还发现块 I/O 计数略小于对象长度，旧的 100% 门槛未满足，原失败记录保留。正式测量采用显式 99% 门槛并逐次公布实际字节数；预检不计入正式负载及错误分母。
- 所有源站摘除时 fresh 完整对象仍 HIT，但已缓存 Range 返回 502；每介质一项 LIMITATION，见 [#16](https://github.com/Monsterwi/bakemono/issues/16)。不具备该条件下的 Range 离线可用性，也没有 stale-if-error。
- 现有 TLS/HTTP/2、存储失败与并发隔离由 Go 集成/回归验证；本轮容量表没有覆盖 TLS/H2、HTTP/3、跨机客户端、公网丢包/RTT、真实磁盘 ENOSPC、掉电或数小时 soak。新 ATS 10.2 尚未安装/适配，本报告不作 ATS 性能排名。
