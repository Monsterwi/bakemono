# Razor HTTP 热路径优化（2026-10-23）

跟踪 [#29](https://github.com/Monsterwi/razor/issues/29)，分支 `perf/http-hotpath`，从 `3277d9a` 继续。测量源码 **`77e5186`**，对照为上一轮优化源码 **`e1b158a`**。本轮实现活动发送缓冲预算、已解析 HTTP 元数据复用及重复工作消除；后续合并/验收见 [#29](https://github.com/Monsterwi/razor/issues/29)，#1 保持打开。

**256 KiB 饱和 C100 吞吐提高 7.5%，完整响应 P99 降低 7.1%；固定 16k RPS 的完整响应 P99 降低 13.1%。100 MiB 吞吐有 1.5%–4.1% 回退，不能称为全场景提升。** 本轮没有重跑 ATS，不能用旧 ATS 成绩计算新的追平比例。

## 方法与口径

专用测试机：双路 Xeon E5-2620 v4，16 个物理核、32 个逻辑 CPU，CentOS 7 / Linux 3.10；Go 1.26.10，GOMAXPROCS=8，HTTP/1.1、loopback、无 TLS，两端启用访问日志。保留 Otter 默认、CRC、缓存格式、失效围栏和完整块提交后 RWW。测试文件为 256 KiB、100 MiB，200 MiB 用于兼容回归。

- **饱和小文件**：checked hey，C32/C100，不绑核；每个并发按 B/O/O/B/B/O 交替运行，每次 10 秒，各版本三次。两个服务同时驻留，单次只对一个施压。
- **固定到达率**：`tools/hotload`，12k/16k offered RPS，最多 100 workers，20 秒，各三轮，版本顺序 B/O、O/B、B/O。延迟从计划发送时间算起，包括客户端排队；TTFB 用 `httptrace`，另测首个正文字节。按完整长度检查每次响应，失败/丢弃单列并以非零状态退出。100 workers 不等于始终有 100 个活跃请求。
- **绑核组**：服务 `0,2,4,6,8,10,12,14`，客户端 `1,3,5,7,9,11,13,15`，分别使用不同 socket 的八个物理核。100 MiB 也采用此布局，C8/C32、B/O/O/B/B/O、各三次 10 秒。
- 表中取各轮指标的中位数，P99 是“三次 P99 的中位数”，不是合并所有请求后的 P99；RSS 是采样峰值的中位数。CPU 成本来自进程累计 CPU 时间差，包含全部线程；GOMAXPROCS 不是硬 CPU 配额。不同绑核组的绝对容量不能直接互比。

## 修改与剖析证据

1. **解析结果随 RAM 条目保存。** 入 RAM 时尝试解码 HTTPInfo，每次读取复制 Header map 和 value slices，避免跨请求修改。每次打开仍验证原始 Doc 的 CRC、身份与版本，磁盘 MISS 回退不变；当前不可变片段只解析一次 Doc 头。两种 RAM 策略均将解码存储的保守估算计入权重，结果随替换/淘汰/删除失效。
2. **消除请求内重复工作。** lookup 返回已解析的响应缓存策略，在新鲜度和发送 Age 时按当前时间推进；请求约束仍逐请求判断。回归曾抓到“lookup 后时间推进却沿用旧 Age”的错误，现已修复。入站请求只派生 context，独立回源生产者仍深复制 Header/URL。
3. **发送缓冲按 runtime 管理活动租约。** 复用标准 `sync.Pool` 的 per-P 路径，加活动字节计数与上限；等待额度可取消，所有结束路径归还。保持逐次写超时、Flush、短写和错误处理。尝试过严格限制空闲保留的共享/分片池和 LIFO 池，饱和吞吐受损，最终没有采用。

同一公开读取接口 `OpenReadCommitted → LoadHTTPInfo → Close`，暖 RAM 条目从 **130 → 17 allocations**，原版实际触发预算测试失败。这只度量元数据打开，不是整个 HTTP 请求的分配率。

单独诊断运行以 16k RPS 各完成 416,000 次请求，CPU 采样 20 秒、trace 3 秒，mutex 采样比例 1/5、block 周期 1 ms。基线为同日较早的同绑核对照；这些诊断数据不进入正式吞吐/延迟表。pprof `alloc_space` 采样累计分配约 **4,083 → 3,139 MiB**，减少约 23%；包含启动、预热和诊断本身，不能等同严格测量窗口的精确分配差。

优化后 CPU flat：系统调用 **56.63%**、内存复制 **7.99%**、CRC **6.96%**；主要仍是网络写出。mutex 多 goroutine 累计等待约 **156 → 140 ms**，不支持将这次收益解释成消除了新的大锁。最终三秒 trace 观测 50 次 GC STW，累计 5.47 ms、最长 0.276 ms；短采样不能证明所有尾延迟由 GC 导致，也不能排除窗口之外的更长暂停。

## 活动缓冲与内存边界

每 runtime 的活动发送缓冲容量为 **`max_requests × 256 KiB`**，默认 256 对应 **64 MiB payload**，按需分配。Stats 增加：

| 字段 | 含义 |
|---|---|
| `ResponseBufferCapacityBytes` | 当前与未排空旧 runtime 的活动容量之和 |
| `ResponseBufferInUseBytes` | 对应活动租约字节数 |
| `ResponseBufferTotalAllocatedBytes` | 对应 runtime 创建以来累计新分配 payload 字节数 |

累计分配会因 GC 清池后重新分配而超过容量，不能当作当前驻留或 RSS；旧 runtime 移除后汇总值也可下降。**空闲缓冲由 GC 管理，没有硬空闲保留量或 RSS 上限。** 热更新期间新旧 runtime 容量相加；这项预算独立于 `CacheWriteBufferBytes` / `BufferReserved`。RAM 解码估算会降低同预算下可驻留条目数；结构、map 空桶、分配器和其他运行时内存仍须靠 heap/RSS 监控。

## 大文件回归与功能验证

100 MiB 热读使用超出 10 MiB RAM 的工作集，OS 页缓存仍可能命中；不是 SSD 物理冷读能力。正式交替对照如下：

| 指标 | e1b158a | 77e5186 | 变化 |
|---|---:|---:|---:|
| C8，MiB/s | 1,024.7 | 982.5 | **−4.1%** |
| C32，MiB/s | 1,005.2 | 989.8 | **−1.5%** |
| C8 CPU，秒/GiB | 5.076 | 5.303 | +4.5% |
| C32 CPU，秒/GiB | 5.766 | 5.834 | +1.2% |
| C8 RSS，MiB | 97.30 | 86.84 | −10.8% |
| C32 RSS，MiB | 99.53 | 100.18 | +0.7% |

均零正文错误、零热请求回源。早先非交替基线约 1,426/1,438 MiB/s，后续同条件对照的基线自身也变为约 1,025/1,005；原因未确认，不把跨时段落差算作代码收益或回退。原值保留在 JSON 的 `earlier_non_interleaved_large`。

另采样两版本 C8 大文件各 20 秒：优化版 CPU flat 清零 **35.12%**、复制 **19.76%**；`readExactRange` 和 `loadFromDisk` 合计约占采样分配 **96%**，基线同样约 96%。本轮元数据复用没有解决大块重复分配/清零；尚未证明小幅回退的唯一根因。下一步应先优化受预算约束的块读缓冲与重复读取，维持 CRC/PURGE/版本边界，再做交替复测。

最终源码功能验收：

- Otter：SSD **14/14**、HDD **14/14**；S3-FIFO：SSD **14/14**。包括小/大文件 SHA256、冷启动合并、跨客户端身份、query、重叠/非对齐 Range、fresh Range 离线、首块 RWW、no-store、源站截断后重试、干净重启。
- HDD/SSD 各通过 **200 MiB GET/HIT/Range**；旧版先写入全新实验缓存，再用最终版恢复 **256 KiB + 100 MiB GET/Range**，均 SHA256 正确且无新增回源。原有缓存文件保留。
- 最终源码普通测试、`CGO_ENABLED=1 GOFLAGS=-race go test ./...`、vet、静态二进制构建通过；Python 工具测试 **20/20**，无跳过。回归覆盖 RAM Header 隔离、损坏校验、覆盖/PURGE/淘汰、304 元数据更新后的正文、时间推进、缓冲耗尽后取消/归还、短写和 Flush 错误。
