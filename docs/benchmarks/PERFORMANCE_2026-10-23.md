# Razor 并发性能剖析与优化（2026-10-23）

基线 `193fe7d`，优化代码 `e1b158a`，跟踪 [#18](https://github.com/Monsterwi/razor/issues/18)。实现位于 `perf/18-hot-hit`，尚未合并 main。保留 Otter 默认、CRC、PURGE 围栏、块提交后 RWW 和原有缓存格式。

**结论：原实现存在不必要的 HIT 串行化，并非当前 Go 架构只能达到旧报告的约 5,000 QPS。** 本轮同机复测与单变量优化后，256 KiB 热命中 C32/C100 吞吐分别提高 **2.30 / 2.48 倍**，达到 ATS 10.2.1 原生缓存的 **70.3% / 71.5%**。C100 P99 反而增加约 **10.8%**，不能称为所有指标都改善。

## 最终同机对照

每组 3 次、每次 5 秒，取中位数；以下使用最后交叉复测的 `baseline-repeat`、`ats-repeat`、`step5-repeat`。所有热请求均零回源 GET、零正文读取错误；256 KiB 组进程实际磁盘读为零。

| 256 KiB 热 HIT | 原 Razor | 优化 Razor | ATS 原生 |
|---|---:|---:|---:|
| C32 QPS | 12,362 | **28,450** | 40,449 |
| C100 QPS | 11,436 | **28,307** | 39,590 |
| C32 P99 完整响应，ms | 5.17 | **3.90** | 1.79 |
| C100 P99 完整响应，ms | 13.63 | **15.10** | 8.28 |
| C32 CPU，μs/请求 | 384 | **285** | 191 |
| C100 CPU，μs/请求 | 398 | **288** | 193 |
| C32 实际 CPU 核数 | 4.73 | **8.12** | 7.71 |
| C100 进程 RSS 峰值中位数，MiB | 34.8 | **44.8** | 59.7 |

CPU/请求由进程 CPU 秒/GiB 换算，256 KiB 对应 4096 请求/GiB。CPU 核数包含进程全部线程，GOMAXPROCS=8 不等于进程硬 CPU 配额。P99 是完整响应耗时，不能当作 TTFB。

旧报告同一基线二进制约 5,000 QPS，本轮首次复测 C32 为 12,648，最后复测为 12,362；ATS 本轮约 40,000，而旧报告约 49,000。**跨日期差异没有归因，不能计入优化收益。** 本轮前后复测相近，收益只相对于本轮基线计算。

## 已证实的原因和修改

| 顺序：逐项叠加，仅改变一个因素 | C32 QPS | C100 QPS | 证据与修改 |
|---|---:|---:|---|
| 原版本 | 12,648 | 11,295 | 并发从 C8 增加后吞吐下降 |
| 1. 新鲜 HIT 不创建 FillToken | 15,399 | 14,947 | `BeginFill` 原先每个 HIT 都锁全部 stripes 并创建快照；只在整对象 MISS 进入共享填充前获取 |
| 2. 已提交对象打开使用共享读锁 | 21,734 | 21,440 | `OpenReadCommitted` 内只有状态读取与私有对象分配，不需要排他锁；仍与 PURGE/关闭互斥 |
| 3. 复用原 32 KiB 传输缓冲 | 22,116 | 22,617 | 原 `streamResponse` 占采样分配约 69%；复用消除每响应一次大分配，吞吐收益小于微基准收益 |
| 4. 池内缓冲增大至 256 KiB | 26,638 | 27,039 | 减少逻辑读写、Doc 重复解析、deadline/Flush 调用；取消、短写和 Flush 错误处理保留 |
| 5. `Release(nil)` 提前返回 | 28,879 | 28,245 | 优化后剖析发现已提交读者没有持有 OpenDir 引用，关闭时仍无意义地获取目录写锁 |

各行是探索阶段三轮中位数，不与最终复测混算，也不把逐项差值视为没有测量噪声的精确归因。网络栈可能拆分一次 Write；没有用逻辑写次数冒充实际 syscall 数量。

安全边界：MISS 的 token 仍早于对应 GET 回源；共享填充内部仍复查已提交缓存。块路径沿用自己的 pre-origin token。PURGE、源站/版本隔离、真正引用释放和磁盘提交逻辑均保留。读锁优化不允许读者附着未提交 writer。

## CPU、锁与分配剖析

诊断构建单独启用 pprof，监听 `127.0.0.1:19060`；正式代码没有增加调试端口。CPU 采样 25 秒，mutex 采样比例 1/5，block 采样周期 1 ms，同时取得 allocs/heap。剖析运行不进入正式吞吐表。

- 基线 mutex 累计等待 **553.50 秒**，其中约 56.5% 归于 `BeginFill` 的解锁栈，43.0% 归于 `OpenReadCommitted`。这是多 goroutine 累计等待及持锁者归因，不能解释成请求墙钟时间占比。
- 前四项优化后等待降至 **12.60 秒**，主要剩余 `Close → Release(nil)`；第五项后为 **1.185 秒**。mutex/block 是采集时的进程累计数据，包含短暂启动及预热，不是严格 CPU 窗口差分。
- CPU 采样从约 **4.68 核**提升至 **8.08 核**。最终 CPU flat：系统调用 **46.08%**、内存复制 **9.70%**、CRC **8.74%**；系统调用上游主要是 HTTP 网络写。占比变化受吞吐提高影响，不代表这些成本绝对变慢。
- 独立传输微基准原来为 **32,816 B/op**，隔离的 32 KiB 复用实验降至 **48 B/op**，最终 256 KiB 池三次为 **53–57 B/op**。其 sink 不经过网络，仅解释分配机制，不作为 HTTP QPS。
- 最终分配热点转向访问日志字段、缓存策略解析、Header 重建和 HTTPInfo 解码。CRC 没有关闭；ATS 本次使用默认 `cache.enable_checksum=0`，完整性成本不同。

## 架构是否限制性能

原实现的共享排他锁是可移除的串行点。本轮在不更换 Go/net/http、RAM 算法、磁盘格式和缓存语义的情况下，将实际 CPU 利用从约 4.7 核提高到约 8 核，证明旧吞吐不是这种架构的固定上限。

另用 Go 1.26.10、GOMAXPROCS=8 的最小 `net/http` 服务，直接从内存一次 Write 返回同一 256 KiB 内容：C32 **39,979 QPS**，C100 **37,916 QPS**。它不包含缓存、CRC、访问日志、准入和 HTTP 缓存语义，**只说明传输路径的可达空间，不是公平的完整产品成绩，也不是理论天花板**。同机客户端、网络栈、调度、CPU 和内存复制都会影响结果。

从观测 CPU 成本估算：最终约 285 μs/请求，8 核持续执行对应约 28,000 QPS，接近实测；ATS 约 191 μs/请求。这说明下一步应降低每请求工作量，而不是仅增加并发或假定换 epoll/io_uring 就能解决差距。8/CPU 成本只是本工况容量估算，不能外推到 TLS、不同对象大小或真实网卡。

本轮尚未测多进程分片、NUMA/绑核、跨主机负载或 CPU 核数扩展曲线，无法给出整个架构的严格理论上限。取消所有串行点也不会消除 CPU、内存带宽和网络限制。

## 大文件与正确性

100 MiB 热读，三轮中位数，单位全部为 **MiB/s**：

| 缓存介质 / 并发 | 原版本 | 优化版本 | 提升 |
|---|---:|---:|---:|
| SSD / C8 | 936 | 1,385 | 48.0% |
| SSD / C32 | 1,006 | 1,429 | 42.1% |
| HDD / C8 | 941 | 1,412 | 50.1% |
| HDD / C32 | 1,021 | 1,438 | 40.8% |

这些组受 RAM/OS 页缓存影响，**不是 HDD/SSD 的物理冷读对比**，本轮没有重跑 ATS 大文件成绩。大文件 CPU/GiB 没有下降：SSD C32 从 3.79 增至 3.98 秒/GiB，HDD C32 从 3.75 增至 3.95；吞吐提升主要伴随更多 CPU 并行执行。SSD C32 RSS 峰值中位数从 83.0 增至 100.8 MiB。样本数不足以产生 hey P99 的大文件组保留缺失值，不填 0。

最终版本 HDD、SSD 各 **18/18 功能通过**：MISS/HIT 正文 SHA256、query 身份、跨 IP/UA 合并、100 客户端小文件冷启动、16 客户端大文件冷启动、重叠及非对齐 Range、源站 503 时已缓存 Range 可读、块提交后 RWW、no-store、源站截断失败后重试、干净重启恢复。两介质 **200 MiB GET/HIT/Range 兼容验证通过**。

普通和 race 测试涵盖取消、PURGE、版本、关闭与存储故障；新增 `TestStreamResponseReuseAndErrors` 和 `BenchmarkStreamResponse` 覆盖缓冲复用、正文、短写和取消。最终代码 `e1b158a` 的 [构建/工具/普通/race CI](https://github.com/Monsterwi/razor/actions/runs/39889789007) 与 [覆盖率 CI](https://github.com/Monsterwi/razor/actions/runs/39889789038) 均通过。

## 代价、限制与下一步

1. **C100 P99 是明确的未解决项**：13.63 → 15.10 ms，约增加 10.8%。本轮没有确认其根因；下一步以 CPU 饱和下的调度/GC/写出批量为假设，使用 trace 和更长固定到达率负载验证。不能用更高 QPS 掩盖尾延迟。
2. 256 KiB 缓冲增加单个活跃响应的内存占用；256 个活跃响应仅这些缓冲理论上约 64 MiB，原来约 8 MiB。`sync.Pool` 可被 GC 清理，但不是严格内存配额，其保留量也不等于瞬时活跃请求数。这个开销不计入 RAM 缓存 value 权重预算，部署须保留余量。
3. 优先研究**不可变、已验证 RAM 表示与已解析元数据复用**，减少每次 HIT 的 HTTPInfo/Header/策略解析和中间复制；必须保持对象版本、失效及损坏检测边界。本轮未实现，不能假设可以安全省略 CRC。
4. 大对象预检和发送仍可能重复读块，整块分配仍多；后续用已预算的块句柄复用验证读放大收益。它不是本轮 256 KiB 整对象 HIT 的主要成因。
5. 两端访问日志开启，但日志格式、缓冲和 HTTP 实现不同；ATS CRC 默认关闭。Linux 3.10、无 TLS、loopback、未绑核、powersave governor，机器上观察到其他后台进程。每组仅 3×5 秒，未做本轮长时间 soak，不能直接当作生产容量或长期稳定性保证。本轮未引入 io_uring/AIO，热 HIT 零读盘也不支持把它们作为当前根因修复。
